## Purpose

Find the highest arrival rate at which 1000 share-group members x concurrency
20 keep north-star queue time near the Redis reference (36 / 77 / 100 ms
p50 / p95 / p99), ramping arrival at 8, 16, 32, and 64 ready partitions with
the record-lock window fixed at 4000.

The acceptance limits match run 5: every task completes exactly once, enqueue
reaches at least 99% of the requested rate, completions end within 3 s of
production, and queue p50 / p95 / p99 are at most 50 / 150 / 300 ms.

## Interpretation

- Doubling per-member concurrency raised the latency-bounded ceiling from
  20,000 to 34,000 RPS and lowered queue time at equal load. Queue time is
  governed mainly by spare slot capacity. Arrivals find an idle member sooner
  when more slots are free, which outweighs the longer generation wait of 20
  records versus 10. This supersedes the earlier suggestion that smaller
  generations are better.
- At 8 partitions, the limit near 26,000 to 28,000 RPS is consistent with the
  in-flight window hypothesis from run 4:
  `8 partitions x 4000 locks / about 1.1 s acquire-to-ack`. Not confirmed
  from broker metrics.
- Above 16 partitions, latency again worsened with more partitions, as in
  run 5.
- The throughput ceiling was not located; 36,000 RPS was the highest rate
  tested. The host was near CPU saturation there, so this laptop cannot
  separate a kq limit from a host limit above about 36,000 RPS.

## Suggestions

1. Continue on dedicated multi-core or cloud hardware, where Kafka, producers,
   and workers do not share one host.
2. Test concurrency 40 and higher on that hardware to find where the longer
   generation wait begins to outweigh added capacity.
3. Size partitions using the in-flight window estimate with headroom, and
   avoid large surpluses of partitions. For this topology, 16 was the best
   tested value.
4. Repeat the best points several times to bound run-to-run variance in p95
   and p99.

## Caveats

- Single Dockerized Kafka broker on localhost, RF=1; one run per point with a
  60 s arrival window.
- Same probe as runs 2 to 5: ready success path only, sleep-only handlers,
  200-byte payloads, queue time measured from just before `Enqueue`.
- The ramps for 16, 32, and 64 partitions started at 24,000 to 32,000 RPS, not
  20,000.
- The acceptance limits are an engineering judgment of "close to" the Redis
  reference, not a production SLO. The Redis figures were not measured with
  this workload or harness.
